goarena Benchmark Lab

Runs the goarena-bench harness on this machine - one OS process per implementation - streams its per-second metrics to live charts, finds the points where an implementation drops in a parameter sweep, and compares the results with the measurements of earlier goarena versions.

    How to read the charts
    
    
    
      
    
        
    Live charts (Run)
    
        
      
          
    • The x axis is seconds since the start of the measured phase of each run, so the
            implementations, which run one after another, are overlaid. Switch to Full run to include the
            populate and warm-up phases.
      • 
          
    • Throughput - million operations per second in each 1-s interval.
      • 
          
    • Latency - p99 (solid) and p99.9 (dashed) of the sampled operations in each interval, in
            microseconds; use the log scale when one implementation has a much heavier tail.
      • 
          
    • GC CPU - share of the available CPU spent by the garbage collector.
      • 
          
    • Memory - solid: process RSS, dashed: Go heap, dotted: off-heap (C) memory, MiB.
            goarena keeps its data off-heap, so its Go heap stays near zero.
      • 
          
    • Vertical lines mark stages of a load profile (ramp / spike) or phases in the full view.
      • 
          
    • Hover a chart to see the values of all series at that time; click a legend entry to hide a series.
      • 
        
    
      
    
      
    
        
    Sweeps, results and history
    
        
      
          
    • A sweep plots a metric against the swept parameter.  red rings mark
            knees: throughput falls by more than 15 %, p99.9 more than doubles, GC CPU rises by more than
            10 percentage points, or (goroutines) the scaling efficiency of a step falls below half of the
            previous step's.
      • 
          
    • The comparison table highlights the best value of every column in bold green; the small
            factor below each value is the ratio to the selected baseline implementation.
      • 
          
    • The latency CDF shows which share of the operations finished within a time; the CCDF (tail view)
            shows the share that took longer, on a log scale - the lower the curve, the thinner the tail.
      • 
          
    • The memory guard projects the peak RSS of every run before it starts and refuses runs above
            min(75 % of RAM, RAM - 6 GiB).
